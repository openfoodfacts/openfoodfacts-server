NAME

ProductOpener::TagsRules - add tags to products with rules defined in YAML files

SYNOPSIS

        use ProductOpener::TagsRules qw/:all/;

        # Pure evaluation (no writes), e.g. for a dry run on a dump
        my $result_ref = evaluate_tags_rules($product_ref);
        # $result_ref->{added}{categories}{"en:caffeinated-colas"} = ["colas-caffeinated"]

        # Evaluate and store the added tags in the "rules" source of tags_sources
        apply_tags_rules_to_product($product_ref);

DESCRIPTION

Tags rules add more precise tags (e.g. categories) to products, from data that is already on the product: categories, ingredients, labels, countries, nutrients, product names and ingredients lists.

Rules are stored in YAML files in the rules/ directory, grouped by product type and by target field, e.g. rules/food/categories/beverages.yml. docs/dev/explain-tags-rules.md explains the format of the rules, the design choices, and how to test a rule.

How it works:

  • load_tags_rules() reads the YAML files, checks each rule, and compiles its conditions to Perl functions (_compile_rule(), _compile_condition()). Invalid rules are reported and skipped.
  • evaluate_tags_rules() selects the rules of the categories of the product, runs their conditions, and checks that the categories they would add are not incompatible with the other categories of the product.
  • apply_tags_rules_to_product() stores the result in the "rules" source of tags_sources. add_tags_rules_data_quality_tags() adds the data quality tags, from check_quality().

The tag fields that conditions can test, and the tag fields that rules can add tags to, are set for each flavor in $options{tags_rules} (lib/ProductOpener/Config_off.pm). Flavors without this setting do not run tags rules.

FUNCTIONS

get_tags_rules ($product_type = undef)

Return the rules for a product type (default: the product type of the server), loaded from rules/[product type]/ the first time it is called.

Invalid rules are logged and skipped. tests/unit/tags_rules.t checks that all rules are valid.

If the flavor has no $options{tags_rules} setting, an empty set of rules is returned.

load_tags_rules ($dir)

Load, check and compile all the rules files (*.yml) in a directory and its subdirectories. Each file contains a list of rules.

Return value

A hash ref (a "ruleset"):

  • rules: list of compiled rules (see _compile_rule()), in file order
  • by_category: required category => list of rules. Used to select the rules to evaluate for a product.
  • by_id: rule id => rule
  • errors: list of errors (strings), prefixed with the file, the rule id and the place of the error in the rule (e.g. "if.ingredients.first"). Rules with errors are not in "rules".

_compile_rule ($ruleset_ref, $file, $rule_from_file)

Check one rule of a rules file and compile it.

$rule_from_file is the rule as read from the YAML file: a mapping with the keys id, description, if, unless, add, tests and comment (see docs/dev/explain-tags-rules.md).

Returns the compiled rule, or undef if the rule has errors (the errors are added to $ruleset_ref->{errors}). The compiled rule is a hash ref with:

  • id, description, file, tests (the match / no_match test products)
  • required_categories: the categories of the top-level "categories" condition of "if". The rule is only evaluated for products in one of those categories (or in a child), and it can only add categories under them.
  • if_sub: function that returns true if all the "if" conditions match the product
  • unless_sub: function that returns true if any of the "unless" conditions matches (undef if there is no "unless")
  • add: field => list of tags to add

Conditions

Conditions are compiled to Perl functions that take an evaluation context (see _new_context()) and return true if the condition matches the product.

The YAML structure gives the logic, so that most rules need no explicit "all" or "any":

  • Under "if" and "all", the keys of a mapping, or the items of a list, must all match (AND).
  • Under "any" and "unless", one of the keys of the mapping, or one of the items of the list, must match (OR).
  • Each item of a list is itself a condition whose keys must all match (AND).
  • A list of tags in a tag condition is an OR: categories: [en:x, en:y] matches products in en:x or in en:y.
  • not: condition: the condition must not match. not: [c1, c2]: none of the conditions matches.

Each compile function takes the path of the condition in the rule (e.g. "if.any[1].ingredients"), used in the error messages, and a reference to the list of errors.

Evaluation context

The evaluation context caches, for one product, the tags used by the conditions.

Conflicts

A rule never adds a category that is incompatible with another category of the product (an existing category, or a category added by another rule), or with a label of the product. Incompatible tags are listed in the incompatible_with:en property of the categories taxonomy, and are also checked on the parents of the categories.

evaluate_tags_rules ($product_ref, $options_ref = {})

Evaluate the rules for a product. The product is not modified.

Options

  • rules: a ruleset returned by load_tags_rules() (default: get_tags_rules() for the product type)
  • rule_ids: list of rule ids: only evaluate those rules

Return value

A hash ref:

  • added: field => { tag => [rule ids] }. Fields are the targets of the add actions (e.g. categories, data_quality_warnings). Conflicts add the en:category-rules-conflict tag to data_quality_warnings.
  • matched: list of the ids of the rules whose conditions matched
  • already: rule id => list of the categories the rule would add, but that the product already has
  • conflicts: list of { rule, tag, with } for categories that were not added because of a conflict

apply_tags_rules_to_product ($product_ref, $options_ref = {})

Evaluate the rules for a product, and store the tags they add in the "rules" source of tags_sources:

        tags_sources.categories.rules = {
                tags => ["en:caffeinated-colas"],
                last_updated_t => 1762800000,
                rules => {"en:caffeinated-colas" => ["colas-caffeinated"]},
        }

The source is only changed when the tags or the rules ids change, and it is removed when no rule adds tags. categories_tags (and other [field]_tags) are regenerated from all sources.

Also sets the misc tags en:tags-added-by-rules (when some tags were added) and en:tags-rule-[rule id] (for each rule that added a tag or a data quality tag).

Data quality tags are not stored: they are added by check_quality(), see add_tags_rules_data_quality_tags().

Returns the result of evaluate_tags_rules().

add_tags_rules_data_quality_tags ($product_ref, $options_ref = {})

Add the data quality tags of the rules (e.g. rules that add data_quality_warnings, and conflicts) to the data_quality_[level]_tags of the product.

Called by check_quality() after it resets the data quality tags.

The rules are evaluated again (they were also evaluated by apply_tags_rules_to_product()). This is cheap: only the rules of the categories of the product are evaluated, and most products have none.

tags_rules_required_categories ($ruleset_ref = undef)

Return the sorted list of all the required categories of the rules (e.g. to select the products to reprocess after a rules change).

build_product_from_tags_rules_fixture ($fixture_ref)

Build a product from a test product of a rules file, so that rule authors only need to write tag ids:

        categories: [en:colas]                    # -> tags_sources.categories (also labels, countries, origins)
        states: [en:ingredients-to-be-completed]  # -> states_tags with parents (computed fields)
        ingredients: [en:water, {id: en:sugar, percent: 10, ingredients: [...]}]  # also sets ingredients_n, unknown_ingredients_n
        nutrients: {cocoa: 55}                    # -> nutrition.aggregated_set (per 100g, as sold)
        product_name_fr: Moutarde douce           # other fields are copied as is

Tags and ingredient ids are canonicalized (e.g. en:citric-acid -> en:e330), so test products can use synonyms.
